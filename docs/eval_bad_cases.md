# 评估 Bad Case 记录

记录检索/生成质量评估中真实跑出来的低分/异常案例，附根因分析。这些是跑出来的
真实结果整理，不是提前写好的示例——写这份文档的目的是给"评测指标好看"的数字提供
反面校验：一个只会展示正面数据的评估体系不可信。

## 检索层：Rerank 负向案例

### q22 —「登录证书过期了怎么更新」

用 `scripts/diagnose_case.py q22` 复现：

| 阶段 | 最佳命中排名 |
| --- | --- |
| 混合检索（无 Rerank） | 第 1 位 |
| 混合检索 + Rerank | 第 8 位（跌出 Top-5） |

混合检索本已把正确片段（"IdP 侧轮换了签名证书，但应用侧的元数据未同步更新"）排到
第 1 位，Rerank 反而把它压到第 8 位，被"订单逾期未付款""账号已锁定"这类明显不相关
的片段挤到前面。

**根因猜测**：查询里的"证书过期"与"逾期未付款"在字面上都含有时间/失效语义，
BGE 交叉编码器可能对"过期"这个词做了过度泛化的语义关联，而没有正确捕捉"登录证书"
这个限定语境。这与文档里另一个已知坑（[README.md](../README.md) 记录的文本表示
不一致导致 Hit@5 下降）机制不同——那次是数据问题（文本表示不统一），这次更像是
模型本身在特定词汇组合上的判别力不足。

**未采取的修复**：没有针对这一条做 prompt 层面或阈值层面的特别处理，因为：
1. 样本量为 1，不足以判断是否是系统性偏差还是个例噪声
2. 强行"修复"单条案例容易过拟合到评估集本身
3. 记录下来比强行修复更重要——让后续如果要迭代 Rerank 策略（比如换模型、加 rerank 后的
   二次过滤规则）时，有一个已知的失败样本可以回归验证
