# 评估 Bad Case 记录

记录检索/生成质量评估中真实跑出来的低分/异常案例，附根因分析。这些是跑出来的
真实结果整理，不是提前写好的示例——写这份文档的目的是给"评测指标好看"的数字提供
反面校验：一个只会展示正面数据的评估体系不可信。

## 检索层：Rerank 负向案例

### q22 —「登录证书过期了怎么更新」

用 `scripts/diagnose_case.py q22` 复现：

| 阶段 | 最佳命中排名 |
| --- | --- |
| 混合检索（无 Rerank） | 第 1 位 |
| 混合检索 + Rerank | 第 8 位（跌出 Top-5） |

混合检索本已把正确片段（"IdP 侧轮换了签名证书，但应用侧的元数据未同步更新"）排到
第 1 位，Rerank 反而把它压到第 8 位，被"订单逾期未付款""账号已锁定"这类明显不相关
的片段挤到前面。

**根因猜测**：查询里的"证书过期"与"逾期未付款"在字面上都含有时间/失效语义，
BGE 交叉编码器可能对"过期"这个词做了过度泛化的语义关联，而没有正确捕捉"登录证书"
这个限定语境。这与文档里另一个已知坑（[README.md](../README.md) 记录的文本表示
不一致导致 Hit@5 下降）机制不同——那次是数据问题（文本表示不统一），这次更像是
模型本身在特定词汇组合上的判别力不足。

**未采取的修复**：没有针对这一条做 prompt 层面或阈值层面的特别处理，因为：
1. 样本量为 1，不足以判断是否是系统性偏差还是个例噪声
2. 强行"修复"单条案例容易过拟合到评估集本身
3. 记录下来比强行修复更重要——让后续如果要迭代 Rerank 策略（比如换模型、加 rerank 后的
   二次过滤规则）时，有一个已知的失败样本可以回归验证

> **补充**：排名下降到第 8 位是真实发生的，但下面「修正」一节核实后发现，
> q22 在 `eval_ragas.py` 里真正拿零分的原因是分数（0.1012）低于阈值 0.15 被过滤，
> 不是排名下降本身——排名和阈值过滤是两个独立的问题，不要混为一谈。

## 生成层：RAGAS 自研指标低分案例

本节基于 `scripts/eval_ragas.py --mode local --save-json eval_ragas_local.json` 的真实
运行结果，运行于 2026-08-07。裁判模型固定为 `qwen-max`，生成模型为本地 Ollama
`qwen2.5:7b`。全量 30 条聚合结果：

| 指标 | 分数 |
| --- | --- |
| context_precision | 61.7% |
| context_recall | 83.3% |
| tool_correctness | 86.7% |
| faithfulness | 0.717 |
| answer_relevancy | 0.600 |

### 真实缺陷：路由把无关知识问题错误路由成写操作确认（q04 / q14 / q27）

三条完全不同主题的知识性问题——q04「SignatureVerificationError 报错」、
q14「早上还好好的，现在一直让我重新登录」、q27「登不上去也不报错就是白屏」——
本地 `qwen2.5:7b` 的路由决策**全部**选中了同一个写工具 `reset_permission_cache`
（描述："刷新账号的权限缓存，使管理员刚做的提权立即生效"），触发写操作确认，
而不是直接基于检索到的知识片段回答。三条的裁判评分都是 faithfulness=0、
answer_relevancy=0——候选答案完全偏离主题。

例如 q27，检索阶段其实拿到了正确片段（context_recall=1.00，"IdP 回调地址与
redirect_uri 不一致"排在靠前位置），问题出在检索之后：路由决策没有采纳这些
知识片段去直接回答，而是莫名其妙选择了一个跟白屏毫无关系的权限缓存刷新工具。

**根因**：本地 7B 模型在路由决策这一步的指令遵循能力不足，`app/agent/router.py`
的 system prompt 已经写明"知识片段已足够回答用户问题...应选 answer"，但模型在
某些输入下仍会倾向选择"看起来像是在做什么操作"的写工具，可能是训练数据里
客服场景与"执行操作"强关联导致的偏置。

**影响**：这类误路由会让用户看到一个无关的"是否要修改系统数据"确认弹窗，
体验上比"信息不足"更糟——用户可能误以为要背这个操作的锁。

### 云端模型对照：qwen-plus 没有真正修复，只是换了一种失败方式

用 `scripts/eval_ragas.py --mode both --case-ids q04,q14,q27 --save-json eval_ragas_router_comparison.json`
跑了对照实验，生成模型分别是本地 `qwen2.5:7b`（local）与云端 `qwen-plus`（cloud），
裁判统一用 `qwen-max`。

| 模式 | q04 actual_tool | q14 actual_outcome | q27 actual_outcome | knowledge_routing_accuracy | faithfulness | answer_relevancy |
| --- | --- | --- | --- | --- | --- | --- |
| local (qwen2.5:7b) | reset_permission_cache | write_confirmation_required | write_confirmation_required | 0.0% | 0.000 | 0.000 |
| cloud (qwen-plus) | create_ticket | max_steps_exceeded | insufficient_information | 66.7% | 0.000 | 0.000 |

`knowledge_routing_accuracy` 从 0% 涨到 66.7%，乍看像是云端模型"修复"了问题，
但看 `faithfulness`/`answer_relevancy` ——**两种模式全部是 0.000，没有任何差别**。

细看 cloud 模式的实际行为：q04 换成了误触发另一个写工具 `create_ticket`（没有变好，
只是换了个错误的工具）；q14 和 q27 都变成了直接拒绝回答（`max_steps_exceeded` /
`insufficient_information`），即使 q27 检索到的证据其实是充分的
（`context_recall=1.0`，命中"IdP 回调地址与 redirect_uri 不一致"），云端模型
依然回复"无法准确回答这个问题，建议提交工单"。

**结论：`knowledge_routing_accuracy` 这个指标本身有盲点**——它只判断"有没有误触发
工具"，不判断"没触发工具时答得好不好"。cloud 模式因为变得更保守（倾向拒绝回答
而不是乱触发工具），指标数字变好看了，但用户体验并没有变好：从"收到一个无关的
写操作确认弹窗"变成"模型说无法回答、去提工单"，两种都是错误答案，只是错误的
呈现形式不同。**不能得出"云端模型修复了路由问题"的结论**——正确的结论是
"两种模型在这 3 条案例上都没有给出正确答案，只是失败模式不同（over-action vs
过度保守），根因可能不在生成模型的选择，而在检索/路由环节传递给生成模型的
信号本身就不够清晰"，需要更大样本才能进一步定位。

样本量为 3，这个结论也不足以外推到全部案例，只能作为"cloud 对照不是免费的银弹"
这一提醒记录下来。

### 评估方法论的局限：eval_ragas.py 的 EVAL_USER_ID 会触发工具调用（q07 / q20 / q21）

q07「欠费了服务什么时候恢复」等三条案例的 `expected_tool` 标注为 `null`
（数据集设计上这些是纯知识性问题），但实际运行 `actual_tool=list_orders`，
`tool_correct` 被判为 `False`。

**根因**：`scripts/eval_ragas.py` 用固定的 `EVAL_USER_ID = "eval-user-no-account"`
驱动 `ChatService`，而 `app/agent/router.py` 会把"当前提问用户的账号 ID"注入
路由 prompt。模型据此认为这是"当前用户在问自己的账单状态"，合理地选择调用
`list_orders` 查真实订单——这在生产场景（真实用户带着自己的账号提问）是**正确
行为**，只是与本评估集"纯知识性问题，不应触发工具"的假设冲突。

**这不是产品缺陷，是评估设计的已知局限**，已经写在
`data/eval_set.json` 顶层 description 里。`eval_set.json` 里的 30 条案例都是
从文档摘出来的通用问法，没有代入具体账号视角提问，与真实场景（用户带着自己账号
问自己的问题）有差异。若要让 `tool_correctness` 真正覆盖工具路由能力，需要
扩充一批"XX 账号欠费了，什么时候能用"这类带上下文的案例并标注对应
`expected_tool=list_orders`——这个扩充尚未做，留在后续待办里。

### 修正：q14 / q22 / q25 context_precision/recall 双零，根因不是"检索盲区"

**这一节是对本文档早期版本的修正**——最初把这三条归为"混合检索+Rerank 组合的
召回盲区"，用 `scripts/diagnose_case.py` 逐条复现后发现结论是错的，改正如下。

三条查询用 `diagnose_case.py`（该脚本设 `MIN_RERANK_SCORE=0.0`）复现，命中排名都不差：

| 案例 | 混合检索排名 | Rerank 后排名 | Rerank 后最佳命中分数 |
| --- | --- | --- | --- |
| q14 | 第 1 位 | 第 4 位 | 0.0504 |
| q22 | 第 1 位 | 第 8 位 | 0.1012 |
| q25 | 第 1 位 | 第 1 位 | 0.1343 |

三条都在 Top-5 内命中，**但三个分数都低于生产配置的 `min_rerank_score=0.15`**
（见 `app/config.py`）。`eval_ragas.py` 跑的是生产默认配置，检索链路里的
`relevance_filter` 阶段会把低于阈值的片段全部丢弃——即使命中片段排名第 1，
分数不过线也会被清空，导致进入生成阶段的候选片段数为 0，`context_precision`/
`context_recall` 自然双双归零，生成模型拿不到任何证据，答案质量随之崩溃。

**真正的根因是：`min_rerank_score=0.15` 这个阈值对这类口语化 hard 查询普遍偏严**，
不是分块策略或召回宽度的问题。q22 那条本来记录成"Rerank 把正确片段从第 1 位
压到第 8 位"是真实发生的（Rerank 确实让排名变差），但排名下降本身不是这条
案例失分的直接原因——即便 Rerank 后仍排第 1 位（如 q25），只要分数不过线，
结果一样是双零。

**影响范围判断**：`scripts/eval_retrieval.py` 的 30 条固定评估集测的是 Hit@K/MRR，
不受这个阈值影响（它看排名，不看阈值过滤后的结果），所以 README 里报告的
Hit@1=90%/Hit@5=96.7% 这些数字仍然成立，不需要修正——阈值只影响真实对话链路里
最终喂给生成模型的片段数量，是 `eval_ragas.py`（走完整链路）才会暴露的问题，
`eval_retrieval.py`（只测检索排名）测不出来。

**未采取的修复**：没有直接调低 `min_rerank_score`，因为这个阈值同时承担着
"检索为空"分支能否触达的职责（见 README「检索质量优化」一节）——调低会让更多
弱相关片段进入生成阶段，需要更大样本验证是否会引入新的幻觉风险，不能只看这
3 条案例就动全局阈值。

## 后续待办（未在本轮完成，留给下一次迭代）

- 针对 hard 口语化查询单独设置更低的 `min_rerank_score`（分难度分层阈值），
  或者验证 query_rewrite 是否能把口语化查询改写成分数更高的表达，需要更大样本
- q31-q38 需要实际跑一次 `eval_ragas.py` 拿到 `tool_routing_accuracy` 的真实数字，
  目前只是设计了案例，还没有运行验证
- 云端对照实验样本量只有 3 条，说明的是"模型选择不是银弹"这个方向性提醒，
  不足以下系统性结论；需要更大样本（比如把 q31-q38 也跑一遍 both 模式）才能
  判断"过度保守拒绝回答"是不是云端模型的普遍倾向，还是这 3 条的个例
- `knowledge_routing_accuracy` 指标本身需要补一个"拒绝回答但证据其实充分"的
  检测：q27 在 cloud 模式下 `context_recall=1.0` 却仍判定「无法回答」，这种
  情况应该单独统计成一类失败（过度保守），而不是被 `knowledge_routing_accuracy`
  计入"正确"、被 `answer_relevancy=0` 简单地和"答案跑题"混在一起——现在两种
  失败方式的裁判分数一样低，但产品含义完全不同，指标设计还需要再细化
